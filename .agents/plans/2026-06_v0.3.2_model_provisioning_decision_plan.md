# v0.3.2 Model Provisioning Decision Plan

Date: 2026-06-05
Status: **APPROVED — PROCEED WITH PLANNING CONSISTENCY GATE THEN IMPLEMENTATION**

## Goal

Choose and provision the best practical local embedding + reranker pair for
Incurator's DB-native search stack under the user's ~2.5 GB VRAM budget, while
keeping setup/update automatic, protecting VRAM by unloading Ollama immediately
before llama-cpp search models are loaded, and exposing model health/refresh
through the backend and Obsidian plugin.

## 2026 Research Findings

### Ollama

Official Ollama docs expose embedding support through `/api/embed`; the docs
index lists generate/chat/embed/tags/pull/ps and related endpoints, but no
first-class rerank endpoint. The FAQ and API docs also document `keep_alive: 0`
on `/api/generate` or `/api/chat` as the API-level unload mechanism, and
`/api/ps` as the way to list models currently loaded in memory. Inference:
Ollama remains useful for chat LLMs and fallback embedding profiles, but the
recommended search model runtime should move to `llama-cpp-python`.

This directly addresses the user's 2.5 GB VRAM constraint: immediately before
loading the llama-cpp embedding/reranker models, Incurator should issue a
best-effort Ollama unload request for the configured Ollama LLM model(s). The
chat client can auto-reload later when synthesis resumes.

Relevant sources:

- https://docs.ollama.com/capabilities/embeddings
- https://docs.ollama.com/llms.txt
- https://docs.ollama.com/faq
- https://docs.ollama.com/api/generate
- https://docs.ollama.com/api/chat
- https://docs.ollama.com/api/ps

### Embedding Candidates

`bge-m3` is still a safe multilingual embedding model:

- Ollama size: 1.2 GB
- context: 8K
- dimension: 1024
- multilingual, dense/sparse/multi-vector-capable model family
- BAAI model card says BGE-M3 does not require query instruction prefixes for
  embedding retrieval

Sources:

- https://ollama.com/library/bge-m3
- https://huggingface.co/BAAI/bge-m3

`qwen3-embedding` is the newer 2025/2026 default candidate:

- Ollama official library supports `qwen3-embedding`
- `qwen3-embedding:0.6b`: 639 MB, 32K context
- `qwen3-embedding:4b`: 2.5 GB, 40K context
- Qwen official model card: 0.6B, 100+ languages, up to 1024 dimensions,
  custom dimensions 32-1024
- Qwen official blog: Qwen3 Embedding/Reranker series was released on
  2025-06-05, Apache 2.0, designed for embedding/retrieval/reranking, supports
  100+ languages and code retrieval, instruction-aware

Sources:

- https://ollama.com/library/qwen3-embedding
- https://huggingface.co/Qwen/Qwen3-Embedding-0.6B
- https://huggingface.co/Qwen/Qwen3-Embedding-0.6B-GGUF
- https://qwenlm.github.io/blog/qwen3-embedding/

### Reranker Candidates

`BAAI/bge-reranker-v2-gemma` is valid as a Hugging Face model, but the exact
current default GGUF source is not verified. BAAI describes it as an LLM-based
Gemma-2B reranker suitable for multilingual contexts and better-performance
use, but it is too risky as an auto-download default without a verified public
GGUF artifact.

Sources:

- https://huggingface.co/BAAI/bge-reranker-v2-gemma
- https://huggingface.co/gpustack/bge-reranker-v2-m3-GGUF

`Qwen3-Reranker-0.6B` is the strongest practical default candidate under the
2.5 GB combined budget:

- official HF model: 0.6B, 100+ languages, 32K context
- SentenceTransformers CrossEncoder usage is documented
- Qwen official blog reports `Qwen3-Reranker-0.6B` outperforming
  `BGE-reranker-v2-m3` on the listed reranking benchmark columns
- `ggml-org/Qwen3-Reranker-0.6B-Q8_0-GGUF` is public, Apache 2.0, 639 MB, and
  documents `llama-cpp-python` / llama.cpp usage
- Earlier search plans correctly warned against arbitrary community
  Qwen3-Reranker GGUFs because broken conversions could omit `cls.output.weight`
  and return near-zero garbage scores. That warning is still valid for random
  community artifacts, but it no longer rules out the corrected `ggml-org`
  Q8_0 artifact. In llama.cpp issue #16407, the maintainer identified bad
  conversion as the likely cause and uploaded `ggml-org/Qwen3-Reranker-0.6B-Q8_0-GGUF`
  as a working artifact with healthy rerank scores. Incurator must still run a
  live smoke validation and fail closed to `no_rerank` if the installed model
  does not rank a relevant passage above an unrelated one.

Sources:

- https://huggingface.co/Qwen/Qwen3-Reranker-0.6B
- https://huggingface.co/ggml-org/Qwen3-Reranker-0.6B-Q8_0-GGUF
- https://qwenlm.github.io/blog/qwen3-embedding/
- https://github.com/ggml-org/llama.cpp/issues/16407
- https://gist.github.com/VooDisss/42bce4eb5c76d3c325633886c5e348ee

`Qwen3-Reranker-4B` can be a higher-quality optional tier, but it is not a good
default for the stated budget:

- community GGUF examples show Q4_K_M around 2.5 GB, leaving no practical room
  for an embedding model if the 2.5 GB budget is combined
- some community Qwen3 reranker GGUF conversions have been reported as broken,
  so any 4B path needs explicit validation before defaulting

Source:

- https://huggingface.co/Voodisss/Qwen3-Reranker-4B-GGUF-llama_cpp

## Recommendation

Default local search model pair:

| Capability | Default | Runtime | Approx model bytes | Reason |
|---|---|---|---:|---|
| Embedding | `Qwen3-Embedding-0.6B-GGUF` / `Qwen3-Embedding-0.6B-Q8_0.gguf` | `llama-cpp-python` | 639 MB | Same runtime as reranker, no Ollama daemon/HTTP dependency, newer multilingual/code retrieval model, 32K context, 1024 dim, fits budget |
| Reranking | `ggml-org/Qwen3-Reranker-0.6B-Q8_0-GGUF` / `qwen3-reranker-0.6b-q8_0.gguf` | `llama-cpp-python` rank pooling | 639 MB | Newer official Qwen reranker family, public GGUF, Q8 quality, fits budget |

Expected combined model bytes: about 1.28 GB before runtime overhead. This leaves
headroom under the user's 2.5 GB target for context/KV/runtime overhead and avoids
the unverified bge-gemma GGUF default.

Fallback / compatibility:

- Keep `bge-m3` as an explicit compatibility fallback profile because it is
  mature, instruction-free, and already implemented.
- Keep Ollama embedding support as a fallback provider, not the default search
  model runtime.
- Add an optional "quality" profile only after validation:
  - `qwen3-embedding:0.6b` + `Qwen3-Reranker-4B` Q4 when the user has more than
    the strict 2.5 GB combined budget.

## Required Implementation Changes After Approval

1. **Default constants/config**
   - Change `DEFAULT_EMBED_PROVIDER` to `llama-cpp`.
   - Change `DEFAULT_EMBED_MODEL` to `qwen3-embedding-0.6b`.
   - Keep `DEFAULT_EMBED_DIM = 1024`.
   - Add embedding GGUF constants:
     - repo: `Qwen/Qwen3-Embedding-0.6B-GGUF`
     - file: `Qwen3-Embedding-0.6B-Q8_0.gguf`
   - Change reranker constants to:
     - provider/model: `llama-cpp::qwen3-reranker-0.6b`
     - repo: `ggml-org/Qwen3-Reranker-0.6B-Q8_0-GGUF`
     - file: `qwen3-reranker-0.6b-q8_0.gguf`
   - Remove the unverified `bge-reranker-v2-gemma-GGUF` default.

2. **llama-cpp embedding provider**
   - Add `LlamaCppEmbedder` in `retrieval/providers.py`.
   - It loads the Qwen3 embedding GGUF with embedding mode, last-token pooling,
     and normalized output.
   - It should reuse the same optional dependency already needed for reranking.
   - It must degrade to `None` when `llama-cpp-python` or the model file is
     missing.
   - Avoid loading and unloading the GGUF per individual query. Use a bounded
     provider cache or engine-scoped cache so the model is reused during a
     single search/reindex operation.

3. **Instruction-aware embedding**
   - Qwen3 embedding benefits from instructions. Add a minimal query/document
     instruction path instead of sending all strings identically.
   - Proposed provider API:
     - keep `embed(texts)` for document chunks
     - add optional `embed_query(texts)` or an `input_role` argument only where
       vector query embedding is produced
   - Use a conservative query instruction such as "retrieve the most relevant
     knowledge-base chunk for the query" and leave document chunks raw unless
     validation shows a document prefix is needed.
   - Preserve `bge-m3` behavior without instruction prefixes.

4. **Ollama VRAM guard before llama-cpp search load**
   - Add a best-effort resource guard in the search provider construction path,
     before `LlamaCppEmbedder` or `LlamaCppReranker` loads a GGUF.
   - Use official Ollama API semantics:
     - `POST /api/generate` with `{"model": MODEL, "prompt": "", "keep_alive": 0}`
       or `POST /api/chat` with `keep_alive: 0`.
     - optionally use `GET /api/ps` to observe loaded models/status.
   - Scope the unload to configured Incurator Ollama LLM models by default
     (`llm.primary`, `llm.fallback`, and configured Ollama model values). Do not
     unload every arbitrary model from `/api/ps` by default, because another app
     may be using Ollama.
   - Make the guard best-effort and non-fatal. If Ollama is unreachable, continue
     loading llama-cpp; if llama-cpp load fails, degrade with a clear warning.
   - Existing `query.py` already calls `client.unload()` before search after
     intent classification. Keep that as a fast path, but also add the provider
     guard so direct `search.query`, MCP search, plugin search, and `wiki reindex
     --embed` get the same protection even when no chat client exists.
   - Record unload attempts/results in runtime status or query trace warnings
     only when useful; avoid noisy warnings on machines without Ollama.

5. **Reranker validation**
   - Ensure `LlamaCppReranker.score()` uses the correct Qwen3 reranker input
     format and rank pooling behavior.
   - Add a live smoke command/test path that scores:
     - query: "What is the capital of China?"
     - doc A: "The capital of China is Beijing."
     - doc B: unrelated gravity text
   - Accept only if doc A scores higher than doc B.
   - Keep failure as `no_rerank` degraded mode.

6. **Provisioning UX**
   - Keep `wiki models ensure/status` as the idempotent low-level API because it
     is useful for setup scripts, updates, CI, plugin IPC, and manual repair.
   - Do not make users learn it as the main workflow.
   - Primary user flows should be:
     - `setup.sh`: runs provisioning unless `INCURATOR_SKIP_MODELS=1`
     - backend/MCP startup: starts Ollama best-effort only
     - `wiki reindex --embed`: reports missing/stale model state and suggests
       or invokes provisioning depending on flag
     - `wiki status`: includes model health summary
     - Obsidian plugin: model status + refresh button calls the same backend
       provisioning path
   - Future polish: consider `wiki doctor --fix models` as the user-facing alias,
     with `wiki models ensure` remaining the machine-oriented subcommand.

7. **Plugin model controls**
   - Add dashboard model panel after P10 trace/insight UI:
     - current embedding model, dimension, pulled/serving state
     - current reranker model, GGUF path, load/score smoke state
     - whether the Ollama pre-search unload guard is enabled and which configured
       Ollama model would be unloaded
     - degraded search mode from latest status/query traces
     - refresh/repair action that invokes backend model ensure
   - Do not expose arbitrary model editing in the first pass. Use config docs for
     overrides.

8. **Docs/tests/testbed**
   - Update English guides first, then faithful `_KR.md` guides.
   - Update setup docs for automatic provisioning and `INCURATOR_SKIP_MODELS`.
   - Update backend unit tests for new constants/repo/file, Qwen instruction
     behavior, llama-cpp embedding degradation, and Ollama unload guard behavior.
   - Run full backend tests.
   - Run testbed smoke with real models when available:
     - `VAULT_ROOT=testbed wiki status`
     - `VAULT_ROOT=testbed wiki add`
     - `VAULT_ROOT=testbed wiki build`
     - `VAULT_ROOT=testbed wiki reindex --embed`
     - `VAULT_ROOT=testbed wiki query "..."`
     - `VAULT_ROOT=testbed wiki lint`
     - Reference Mode/Zotero behavior must be included.
