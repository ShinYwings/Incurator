# v0.3.2 — Search Internalization (retire qmd → in-DB FTS5 + chunked vector + RRF + expansion/rerank)

Date: 2026-06-04
Status: **APPROVED FOR ACTIVE SPECS / GUIDES / TESTS / RUNTIME CODE**

## 0. Why this exists (the verdict the user asked for)

Two questions were raised about the cleanup plan's §2 (GraphRAG) and §2.2 (qmd):

### A. Microsoft GraphRAG infrastructure — VERDICT: do NOT adopt; keep homegrown. (I agree with the plan.)
- Microsoft `graphrag` is explicitly **demonstration code, not an officially
  supported offering**, and its cost-optimized variant (LazyGraphRAG) lives inside
  **Azure Discovery / Azure Local**, i.e. hosted, not a local-first library. Its
  default storage/vector/config surface is server/Azure-oriented.
- Incurator already encodes the GraphRAG-equivalent IR in `state.sqlite`
  (`graph_entities`, `graph_relations`, `community_reports`, `synthesis_nodes`)
  **plus** HippoRAG-style `memory_paths`. Adopting the package would create a
  **second indexing product + second config surface inside the vault** and fight
  the source-span/provenance + Reference-Mode + `curate.yml` KRS contracts.
- **Selectively borrow** (behind existing contracts), not adopt:
  - Leiden (or hierarchical Leiden) community detection to replace the current
    connected-components pass, behind the `community_reports` contract.
  - DRIFT-style query routing as an evolution of local/global/explore.
  - Incremental-invalidation discipline for reports/synthesis (we already have
    `artifact_dependencies` + `dependency_hash` — formalize it).
  This is incremental and does NOT require Microsoft's package.

### B. qmd search backend — VERDICT: keeping qmd is NOT the best long-term answer; it was only a fine *cleanup-pass* stopgap. Replace it with in-DB hybrid search, but not with naive embeddings.

The decisive argument is **philosophical consistency**, not micro-optimization:

- v0.3.1's core invariant: **`state.sqlite` is the single source of truth;
  `.curator/Collections/` markdown is a "derived, disposable projection."**
- But **qmd can only search the markdown projection** (it indexes files on disk).
  That makes the projection **load-bearing**, which silently revives the exact
  **DB↔file drift** v0.3.1 was designed to eliminate, and forces an
  emit→reindex step on every change.
- qmd is also an **external binary** (npm `@tobilu/qmd`): install/CI friction,
  version drift, and it **owns embeddings + vector store + rerank** outside our
  DB — so our "source of truth" doesn't actually own its own search index.

The mature, proven alternative at our scale is **in-DB hybrid search**:
- **Lexical:** SQLite **FTS5** (BM25) over the authoritative records
  (`knowledge_units.statement`, `synthesis_nodes.statement/title`,
  `community_reports.summary/full_content`, `source_spans.text_preview`). FTS5 is
  bundled in Python's SQLite — **zero new dependency**.
- **Vector:** embeddings stored as BLOBs in `state.sqlite`; nearest-neighbour by
  **in-process cosine (NumPy brute force)** — at personal-KB scale (hundreds–low
  thousands of nodes) this is <50 ms and needs **no new dependency**. Optional
  `sqlite-vec` (pip wheel) as an accelerator later if a vault grows large.
- **Fusion:** Reciprocal Rank Fusion (RRF) of the two ranked lists — the standard
  FTS5+vector pattern.
- **Typed query expansion:** default retrieval must expand a plain user question
  into structured `lex`, `vec`, and `hyde` variants. Deterministic expansion
  runs first; a configured query-expansion model must run when available.
- **Rerank:** answer-producing retrieval must rerank fused candidates with a
  dedicated reranker when configured. This can be a local cross-encoder/search
  reranker, a Python GGUF-backed reranker, or a validated search-fine-tuned LLM
  rerank prompt. A generic chat prompt is allowed only as a degraded fallback,
  never as the parity target.

Net effect: search now queries the **source of truth directly**; the markdown
projection becomes **genuinely optional** (Obsidian-only convenience), removing
the external binary AND the drift liability in one move. This is the change that
makes the v0.3.1 compile-model philosophy actually true.

> Critical correction from qmd source review: a simple Ollama embedding drop-in is
> **below parity**. qmd's quality comes from typed query expansion (`lex`/`vec`/
> `hyde`), context/intent steering, chunk-level embeddings, RRF, and a
> cross-encoder-style reranker. v0.3.2 must replicate or exceed that pipeline
> natively in Python while searching the authoritative DB.

## 1. Scope

In: lexical+chunked-vector+RRF search inside `state.sqlite`; embedding generation/
storage/invalidation; typed query expansion; intent/context injection; rerank
in-process; trace persistence; `search.py` rewrite; `evidence.py._qmd_hits`
replacement; `wiki reindex` semantics; MCP/plugin search/status; remove qmd from
setup/CI/docs; dashboard click-to-use for traces/insights; specs + guides EN/KR;
tests + testbed smoke.

Out (separate later goals): Leiden community detection; DRIFT routing; sqlite-vec
acceleration unless latency crosses the documented threshold; broad plugin-side
search UI redesign beyond the approved dashboard trace/insight click-to-use
queue.

## 3. Phased implementation
1. **Spec + trace schema**: bump synchronized v0.3.2 specs; add
   `search_documents`, `search_chunks`, `search_embeddings`, `search_index_meta`,
   and `query_traces`; define qmd-parity acceptance criteria.
2. **Lexical materializer**: FTS5 over authoritative DB rows, with robust parsing
   for exact phrases, negation, hyphen/dotted identifiers, prefix matching, and
   Korean/CJK via trigram fallback.
3. **Chunking + embeddings**: semantic chunks with stable positions, source-span
   provenance, model/provider/dimension/fingerprint, and dependency-hash
   invalidation. Whole-node embeddings alone are explicitly insufficient.
4. **Typed expansion**: deterministic expansion plus configured LLM/query-expander
   support for `lex`, `vec`, and `hyde`; preserve `intent` and DAG/KRS context.
5. **Hybrid fusion**: RRF with qmd-compatible defaults (`k=60`, original-query
   weighting, candidate limit, top-rank bonus) and full contribution trace.
6. **Rerank**: rerank best chunks after RRF with a configured cross-encoder/search
   reranker or search-fine-tuned model; blend rerank and RRF position-aware.
7. **Wire + retire qmd**: replace `_qmd_hits`, CLI/MCP/plugin/runtime status, and
   `wiki reindex`; remove qmd binary/config/template/docs once parity tests pass.
8. **Dashboard click-to-use**: add trace list/show, insight show/reject/promote,
   and correction-propose hidden plugin commands; render Trace/Insights tabs.
9. **Tests + testbed**: parser, expansion, chunking, FTS/vector/RRF/rerank,
   degradation, trace persistence, plugin dashboard actions, qmd-parity smoke, and
   Reference Mode/Zotero source checks.

Current execution gate:

- Specs were bumped in lockstep to `v0.3.2`; `v0.3.1` active root specs were
  archived under each spec domain's `archives/` folder.
- Active guides are being updated before runtime code, including paired Korean

- Tests must be added before final runtime wiring. The first implementation

  lexical search, trace persistence, and configured rerank hooks. Chunk-vector

  model is configured, but the architecture must expose those stages and traces
  now so naive whole-record embeddings cannot become the accepted parity path.

## 4. Risks / decisions to confirm (consider `/grill-me`)
- Embedding provider for offline/local vaults. qmd defaults differ from likely
  Python choices; `bge-m3` may be stronger for Korean/English, while
  `nomic-embed-text` is simpler locally. The spec must pin provider/model/dim.
- Reranker provider. qmd uses a Qwen3 reranker via node-llama-cpp ranking
  context; Python must choose either a local cross-encoder/search model,
  llama-cpp-python/GGUF, sentence-transformers, or an explicitly validated LLM
  rerank provider. Generic chat rerank is degraded mode only.
- Query-expansion provider. qmd has a fine-tuned `qmd-query-expansion` GGUF model;
  Python must decide whether to use a local GGUF, a small transformer pipeline,
  or a prompt contract that is benchmarked against qmd.
- Whether to keep emitting `.curator/Collections/` markdown at all once search no
  longer needs it (recommend: keep as opt-in Obsidian projection, default off or
  cheap, decoupled from search).
- sqlite-vec now vs. brute-force-now/accelerate-later (recommend: brute-force now;
  zero dep; revisit if a real vault exceeds ~50k nodes).
