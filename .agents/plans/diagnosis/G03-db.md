## Findings

### [G03-db-1] (a) S1 — LWW/since uses `sources.last_ingested`, which is NULL for pending sources → pending-source edits never sync, never export incrementally
- Loc: backend/src/curator/db_sync.py:86 (`_UPDATED_AT_COL["sources"] = "last_ingested"`); consumed at db_sync.py:264 (export `since`), db_sync.py:413/424-432 (`_lw_upsert`), db_sync.py:373-377 (`_apply_tombstone`).
- Evidence: `sources.last_ingested` is "NULL if not yet processed by LLM" (db.py:87). Three consequences: (1) Incremental export `SELECT * FROM sources WHERE last_ingested >= ?` (db_sync.py:264) — NULL fails the `>=` comparison, so every `pending`/`force_pending`/`error` source is silently omitted from a `since` export. (2) On import, `_lw_upsert` reads `local_ts = existing[0] or ""` and compares `remote_ts > local_ts` (db_sync.py:425-427); for two pending rows both `last_ingested` are NULL→`"" > ""` is False, so a peer's newer pending-source metadata (status changes, tags, domain, import_origin, is_reference) is always classified `skipped` and never applied. (3) `_apply_tombstone` guard at db_sync.py:376 `local_record[0] or "" >= deleted_at` — a pending local row has `""`, never `>= deleted_at`, so the delete is applied; that branch is actually OK, but it cannot protect a freshly-edited-but-never-ingested local row from a stale peer tombstone.
- Fix sketch: `sources` has no single monotonically-updated column. Add an `updated_at TEXT` column (touched on every status/metadata write) and use it as the LWW key; or, as an interim, `COALESCE(last_ingested, added_at)` everywhere `_UPDATED_AT_COL["sources"]` is used. The export `since` filter must also handle the NULL case (`WHERE COALESCE(updated_at, added_at) >= ?`).
- Blast radius: Cross-device sync of source registry. Pending/errored sources silently diverge between devices; LWW determinism for the `sources` table is wrong. Touches db_sync export/import/tombstone paths.
- Suggested PR: `fix(db): use a real updated_at for sources LWW/since sync (pending rows have NULL last_ingested)`

### [G03-db-2] (a) S2 — `accept_entity_merge` re-points relation endpoints with raw UPDATEs, bypassing the (src,tgt,type) dedup → can create duplicate and self-loop relation rows
- Loc: backend/src/curator/db.py:2898-2912 (endpoint rewrite in `accept_entity_merge`); contrast db.py:2609-2615 dedup SELECT in `upsert_graph_relation`.
- Evidence: There is no UNIQUE index on `graph_relations(source_entity_id, target_entity_id, relation_type)` (grep confirms none). `upsert_graph_relation` dedups by SELECT-then-INSERT, but `accept_entity_merge` re-points endpoints via direct `UPDATE graph_relations SET source_entity_id=survivor ...`. If both an origin→X and survivor→X relation of the same type exist, the merge produces two identical (survivor, X, type) rows; if origin→survivor existed, it becomes a self-loop survivor→survivor. The reversal lineage (db.py:2877-2897) is captured correctly, so reversal still works, but the forward graph now carries duplicates that downstream lifecycle compilation (`_classify_relation_lifecycle`) only partially absorbs (self_loop quarantine handles the loop; the duplicate non-loop row is NOT deduped — both can become `active` and inflate community support/topology).
- Fix sketch: After re-pointing, collapse duplicate (src,tgt,type) rows into one (merging supports), and either skip or explicitly quarantine the self-loops; record the collapse in the rewrite_json so reversal can restore them. Alternatively re-route through `upsert_graph_relation`'s dedup path.
- Blast radius: Entity-merge correctness; graph topology and community support counts (§21.5 corroboration). Reversibility audit (byte-identical pre-merge) may also be affected if a duplicate is later collapsed.
- Suggested PR: `fix(db): dedup duplicate/self-loop relations created by entity-merge endpoint repointing`

### [G03-db-3] (h) S2 — Two distinct timestamp formats coexist; `vision_page_cache` / `page_hashes` use naive local-time `datetime.now().isoformat()` while everything else uses UTC `_now_iso()`
- Loc: backend/src/curator/db.py:1707-1708 (`vision_cache_put`), db.py:1730-1731 (`update_page_hash`); contrast `_now_iso()` db.py:709-712 (UTC, `...Z`).
- Evidence: `_now_iso()` returns `YYYY-MM-DDTHH:MM:SSZ` (UTC). `vision_cache_put` and `update_page_hash` call `datetime.datetime.now().isoformat()` — machine-local time, no `Z`, with microseconds. These are device-local tables (excluded from sync via EXCLUDE_TABLES, so no cross-device LWW corruption), so the impact is limited to inconsistent/ambiguous `created_at`/`last_synced` values (local TZ, not comparable to the UTC fields used everywhere else). Low correctness risk but a latent footgun if either column is ever made an LWW key or compared against a `_now_iso()` value.
- Fix sketch: Replace both with `_now_iso()` for repo-wide consistency.
- Blast radius: Local timestamps only (page_hashes, vision_page_cache are device-local). Cosmetic/diagnostic today; trap for future LWW use.
- Suggested PR: `fix(db): use UTC _now_iso() for page_hashes and vision_page_cache timestamps`

### [G03-db-4] (h) S2 — `_apply_tombstone` swallows DELETE failures with bare `except Exception: pass`, masking FK/lock errors but still recording the tombstone
- Loc: backend/src/curator/db_sync.py:381-384.
- Evidence: `try: conn.execute("DELETE FROM ... WHERE pk = ?") except Exception: pass`. If the delete fails (e.g. an FK ON DELETE RESTRICT, a locked table, a malformed `record_id`), the exception is silently dropped, yet the very next statement (db_sync.py:395-399) records the tombstone as if the deletion succeeded. The local row survives but the tombstone now propagates to peers, producing a divergent state (peers delete a row this device still serves). No log line is emitted on the swallow.
- Fix sketch: At minimum log the exception with `logger.warning(...)` and do NOT record the tombstone when the delete actually failed; or let the exception propagate so the import transaction rolls back atomically.
- Blast radius: Cross-device deletion correctness; silent divergence. db_sync import path.
- Suggested PR: `fix(db_sync): stop swallowing tombstone DELETE failures and recording a tombstone for a delete that did not happen`

### [G03-db-5] (e) S2 — `db.py` is a 4679-line god-file mixing ~12 unrelated subsystems behind a single module
- Loc: backend/src/curator/db.py (whole file); subsystem seams visible at the `# --- xxx ---` banners (jobs ~1321-1594, source_spans ~1957, knowledge_units/claim_supports ~2127, graph entities/relations/merges ~2520-2977, relation lifecycle/topology ~2980-3217, community rebuild ~3340-3717, graph audit ~3791-3934, prompt_runs ~3982, curation_plans ~4072, insight_candidates ~4128, synthesis_nodes ~4250, search ~4325-4679).
- Evidence: Schema DDL, migrations, job queue, span/unit/claim-support storage, the entire Plan C graph-quality engine (Tarjan bridge detection, union-find communities, lifecycle classification, deterministic community rebuild), graph audit, search corpus/FTS, and query traces all live in one file. The deterministic graph compiler (`detect_bridge_risk_relations`, `compile_relation_lifecycle`, `rebuild_graph_generation`, `reconcile_source_change`, `graph_audit`) is real algorithmic logic, not thin DB accessors, and is the hardest-to-test part buried among CRUD.
- Fix sketch: Extract cohesive seams into submodules (e.g. `db/schema.py`, `db/migrations.py`, `db/jobs.py`, `db/graph_quality.py`, `db/search.py`) re-exported from `db/__init__.py` to preserve the `from . import db` call surface. No behavior change; pure structural split. Verify with existing pytest before/after.
- Blast radius: Import surface is wide (`from . import db` used across the backend) — must preserve every public symbol. High-value but mechanical refactor; do under green tests.
- Suggested PR: `refactor(db): split state-DB god-file into cohesive submodules (no behavior change)`

### [G03-db-6] (g) S2 — `refresh_support_freshness` does a full scan of all verified `claim_supports` with a per-row UPDATE loop (O(N) round-trips inside the publish gate)
- Loc: backend/src/curator/db.py:2387-2429.
- Evidence: It selects every `claim_supports` row with `support_status='verified'` joined to `source_spans`, iterates in Python, and issues one `UPDATE claim_supports ...` per stale row plus one `UPDATE knowledge_units ...` per stale unit. On a large corpus this is a full-table pass on every publish (the docstring says it joins the caller's open transaction, so it runs on the publish hot path). The stale detection itself is a single SQL set difference (`WHERE ss.content_hash IS DISTINCT FROM cs.evidence_hash`) and the unit/support marking could be two set-based UPDATEs instead of a Python loop.
- Fix sketch: Replace the Python loop with two set-based UPDATEs: mark supports stale via the join predicate in one statement; mark owning units stale via `UPDATE knowledge_units ... WHERE id IN (SELECT DISTINCT knowledge_unit_id FROM claim_supports WHERE support_status='stale' ...)`. Return the affected unit ids via a `RETURNING` clause or a follow-up SELECT.
- Blast radius: Publish/reconcile latency on large vaults; no correctness change if the predicate is preserved (note: keep the `current_hash IS NULL → stale` semantics).
- Suggested PR: `perf(db): set-based support-freshness recheck instead of per-row UPDATE loop`

### [G03-db-7] (a) S2 — `reconcile_source_change` LIKE-prefilter on `source_span_ids` JSON can MISS rows (false negative under-staling) because a JSON array has no delimiter guaranteeing the quoted-needle boundary the comment assumes
- Loc: backend/src/curator/db.py:3763-3786 (the `source_span_ids LIKE ?` candidate prefilter with needle `f"%{json.dumps(sid)}%"`).
- Evidence: The comment (db.py:3755-3762) argues the quoted needle `"SPAN-1"` never matches `["SPAN-10"]` because of the closing quote. That holds for span ids, BUT the design relies on `json.dumps(list)` always emitting `"id"` tokens with quotes intact — which it does today. The remaining risk is correctness-by-comment: the exact set-intersection guard at db.py:3777-3778 only runs over rows the LIKE prefilter returned, so any LIKE false-negative (e.g. if a future caller stores `source_span_ids` non-canonically, or with whitespace `[ "SPAN-1" ]`, which `json.dumps` with default separators would not produce but an imported peer row or hand-edited row could) is permanently invisible: the row is never a candidate, so its stale support is never marked, leaving an `active` relation citing a removed span. The Python guard "cannot recover" a prefilter miss (the comment admits this for the quote case but not the whitespace/format case).
- Fix sketch: Either (a) drop the LIKE prefilter and chunk the verified-support scan directly (simpler, slightly slower), or (b) normalize `source_span_ids` storage to a canonical no-space form on every write AND on import, then the quoted-needle invariant is airtight. Given graph_relation_supports rows arrive via cross-device import (`_do_upsert` copies the peer's JSON verbatim, db_sync.py:452-458), normalization at the read boundary is the safer fix.
- Blast radius: Source edit/delete reconciliation (§27.8). Under-staling leaves dangling `active` relations; graph_audit would later flag `report_finding_without_active_support` / `active_relation_insufficient_support`, so it is detectable but not auto-corrected.
- Suggested PR: `fix(db): make reconcile_source_change span-prefilter robust to non-canonical source_span_ids JSON`

### [G03-db-8] (h) S3 — `connect()` context manager has no explicit rollback; a write that raises after partial statements relies on close()-time discard, and `commit()` is only reached on the happy path
- Loc: backend/src/curator/db.py:1250-1267.
- Evidence: `try: ... yield conn; conn.commit() finally: conn.close()`. There is no `except: conn.rollback()`. In Python's sqlite3 (default deferred-transaction mode), `close()` on a connection with an open transaction discards uncommitted changes, so atomicity is preserved in practice — BUT this is implicit and fragile: it depends on sqlite3 not being in autocommit/`isolation_level=None` mode (it is not, by default). Any future change to `isolation_level`, or a DDL statement (which auto-commits in some modes) executed mid-block before the exception, could leak a partial write. The single-statement accessors are fine; the multi-statement ones (`accept_entity_merge`, `rebuild_graph_generation`, `delete_source_spans`) are the ones that matter, and they correctly thread a shared `conn` via `_maybe_conn` so the whole multi-step op is one transaction — good — but the outermost owner still has no explicit rollback.
- Fix sketch: Add `except Exception: conn.rollback(); raise` before/around the `finally`, to make atomicity explicit rather than relying on close-time discard semantics.
- Blast radius: Defensive hardening; no observed live bug. Touches every DB call (single shared context manager) so validate carefully.
- Suggested PR: `fix(db): explicit rollback in connect() context manager on exception`

### [G03-db-9] (b) S3 — `init_db` and `connect` both run the full `SCHEMA_SQL` + `_apply_migrations` on every connection; migration work (table-rebuilds, PRAGMA-gated FK drop) re-executes on the hot path
- Loc: backend/src/curator/db.py:1216-1246 (`init_db`) vs db.py:1254-1264 (`connect`); migrations at db.py:742-913.
- Evidence: `connect()` calls `conn.executescript(SCHEMA_SQL)` and `_apply_migrations(conn)` on EVERY open (comment: "self-heal for existing empty/corrupted state DB files"). `_apply_migrations` runs `_column_names` PRAGMA probes and `SELECT sql FROM sqlite_master` checks for every table on every connection. The expensive table-rebuild branches (ingest_jobs FK drop db.py:822-881, deleted_records CHECK rebuilds db.py:1053-1081 / 1176-1206) are guarded by idempotency checks so they no-op after the first run, but the dozen+ PRAGMA/`_add_column_if_missing` probes still execute per connection. There is no `schema_version`-gated fast path: a healthy current-version DB pays the migration-probe cost on every short-lived CLI invocation.
- Fix sketch: Gate `_apply_migrations` (and possibly the `executescript(SCHEMA_SQL)` self-heal) behind a cheap `PRAGMA user_version` / `schema_version` check so a DB already at `SCHEMA_VERSION` skips the probe pass. Keep the self-heal reachable for the genuinely-empty/corrupted case.
- Blast radius: Per-invocation latency (matters for the many small `wiki status`/job-poll calls). Must not break the self-heal contract for empty DBs.
- Suggested PR: `perf(db): version-gate per-connection migration probing`

### [G03-db-10] (a) S3 — `upsert_knowledge_unit` UPDATE branch resets nothing for the support/formula/generation columns but ALSO never clears `atom_node_id`/`prompt_run_id` to NULL when callers pass None mid-life — and silently ignores a passed `unit_id` that does not exist by minting a NEW row with that id
- Loc: backend/src/curator/db.py:2143-2185.
- Evidence: When `unit_id` is given but no row exists (db.py:2149-2153 finds nothing), control falls through to `new_unit_id = unit_id or _new_id("KNU")` (db.py:2170) and INSERTs with the caller-supplied id. That is probably intended (upsert), but combined with the UPDATE branch it means a caller cannot tell whether their `unit_id` updated an existing row or created a new one (both return the id). Separately, the UPDATE branch (db.py:2154-2168) writes `source_id`, `confidence`, `truth_status`, `atom_node_id`, `prompt_run_id` directly from args — so calling it with the defaults (e.g. `confidence=0.0`, `atom_node_id=None`) to update only the statement will silently zero `confidence` and null `atom_node_id`. There is no field-level "preserve if None" like `upsert_community_report` uses (`_pick`). This is an easy data-loss footgun for partial updates.
- Fix sketch: Either document that this is a full-row replace (and require callers to pass the full prior state), or adopt the `_pick`/COALESCE preserve-on-None pattern used by `upsert_community_report` for the optional columns.
- Blast radius: Any caller doing a partial KNU update. Verify against ingest_llm/compiler callers before changing semantics.
- Suggested PR: `fix(db): make upsert_knowledge_unit partial-update safe (preserve unset optional columns)`

### [G03-db-11] (h) S3 — `recover_stale_jobs` requeues ALL running jobs unconditionally and does not increment/cap retry_count, so a job that crashes the worker can loop forever on restart
- Loc: backend/src/curator/db.py:1432-1442.
- Evidence: On process restart it flips every `state='running'` row back to `queued` with `phase='recovered'`, leaving `retry_count` untouched. If a specific job deterministically crashes the worker (poison message), each restart re-queues it and it crashes again — there is no max-retry guard here (the explicit retry path `requeue_job_for_retry` does track a count, but recovery bypasses it). Also resets no `progress` field, so a recovered job shows stale progress until the worker overwrites it.
- Fix sketch: On recovery, increment `retry_count` and route jobs that exceed a cap to `failed` (with an explicit "exceeded recovery retries" error) instead of re-queueing; reset `progress=0.0`.
- Blast radius: Job queue resilience on restart. Low risk to change (additive guard).
- Suggested PR: `fix(db): cap recover_stale_jobs requeues with retry_count to prevent poison-job restart loops`

### [G03-db-12] (b) S3 — `import json` re-imported locally inside functions despite the module-level `import json`
- Loc: backend/src/curator/db.py:1810 (inside `list_source_pdf_pages`), db.py:1856 (`json_dumps`), and the module-level `import json` at db.py:14.
- Evidence: `json` is imported at module top (db.py:14) and used throughout, yet `list_source_pdf_pages` (db.py:1810) and `json_dumps` (db.py:1855-1858) do a redundant local `import json`. Likewise `vision_cache_put`/`update_page_hash` do local `import datetime` (db.py:1707, 1730) while `_now_iso` imports it locally too (db.py:710) — no module-level datetime import. Harmless but dead-weight / inconsistent.
- Fix sketch: Drop the redundant local `import json`; optionally hoist `import datetime` to module scope.
- Blast radius: None (cosmetic). Pure cleanup.
- Suggested PR: `chore(db): drop redundant local imports`

## Positives (keep / do-not-break)
- The `_chunked` / `_SQL_VAR_CHUNK` discipline is applied consistently (delete_source_spans, reconcile_source_change, migration backfill) to stay under SQLITE_MAX_VARIABLE_NUMBER — a real, tested concern; do not collapse these back into single IN-lists.
- `_maybe_conn` is a clean seam letting multi-step compiler ops (accept_entity_merge, rebuild_graph_generation, delete_source_spans, reconcile_source_change) run inside ONE caller-owned transaction for atomic publish (§26.3/§27.8). Preserve this contract during any refactor — do NOT have these helpers open their own `connect()` when a `conn` is threaded.
- The Plan C graph-quality engine is carefully built: iterative Tarjan bridge detection with subtree-size density gating (db.py:3042-3086), deterministic union-find communities rooted at the smaller id (db.py:3312-3337), and content-vs-identity hash separation in `rebuild_graph_generation` (member_hash/support_hash identity vs dependency_hash content, db.py:3614-3645) giving true idempotent no-op rebuilds. This is subtle and correct; treat as load-bearing.
- The migration helpers correctly create support/lifecycle/parent indexes AFTER the ALTER adds their columns (the schema comments at db.py:316-318/392-394/421-422 explain why the base CREATE TABLE IF NOT EXISTS cannot do it for pre-existing tables). Do not "simplify" those indexes back into SCHEMA_SQL.
- `upsert_community_report` `_pick` preserve-on-None pattern lets the deterministic skeleton pass and the LLM prose pass write the same row without clobbering — a good model the KNU upsert should copy (see G03-db-10).
- db_sync `_DEVICE_LOCAL_COLUMNS` correctly shields `sources.external_path` (per-machine Reference-Mode path) from peer clobber on UPDATE while still letting it flow on INSERT — keep this.
- The `entity_aliases` partial UNIQUE index (`WHERE entity_id IS NOT NULL`, db.py:445-447) correctly allows homonyms (one normalized surface → many entities) while blocking exact duplicate resolved rows. Subtle and intentional.
