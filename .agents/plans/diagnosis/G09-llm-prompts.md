## Findings
### [G09-1] (e/f) S2 - Live prompt behavior still bypasses the PromptContract registry
- Loc: docs/specs/system_behavior/SYSTEM_BEHAVIOR.md:1036, docs/specs/system_behavior/SYSTEM_BEHAVIOR.md:1056, backend/src/curator/prompts.py:101, backend/src/curator/prompts.py:126, backend/src/curator/prompts.py:197, backend/src/curator/prompts.py:641, backend/src/curator/ingest_raw.py:482, backend/src/curator/ingest_raw.py:674, backend/src/curator/sync.py:807, backend/src/curator/lint.py:935, backend/src/curator/mcp_server.py:2703
- Evidence: The spec says prompt behavior is no longer scattered and that prompt text in `prompts.py`/`query.py` moves into `backend/src/curator/prompting/families/*` with no compatibility wrappers kept. The newer pipeline paths do use `prompting.REGISTRY` and `run_prompt`, but `prompts.py` remains a 1152-line live prompt module with builders for summary, image description, atom/concept markdown generation, curation planning, logic verification, contradiction resolution, persona interview, lint relink, context update, and backprop insight extraction. Those builders are still imported by ingest, sync, lint, CLI, MCP, and backprop code. These calls do not get `PromptContract` identity, output models, validator declarations, retry policy, or `PTR-` traces by construction.
- Fix sketch: Make an inventory of every live `prompts.py` builder, split it into (1) prompt families that should become typed `PromptContract`s, (2) UI/interview prompts that need a separate registered contract family, and (3) dead retired prompts. Migrate callers to `prompting.REGISTRY.get(...)` plus `run_prompt` where persistence/tracing matters, then delete migrated builders rather than leaving wrapper aliases.
- Blast radius: `wiki add` L1 summary/image extraction, legacy ingest-LLM atom drafting, `wiki sync` logic verification, `wiki lint --fix`, contradiction repair flows, persona wizard, MCP correction/resolution flows, prompt trace completeness, and docs that promise registry coverage.
- Suggested PR: `refactor/prompt-contract-coverage`

### [G09-2] (a/e) S2 - Prompt v2 cannot currently enforce cross-model JSON/profile parity
- Loc: backend/src/curator/prompting/runner.py:151, backend/src/curator/llm.py:408, backend/src/curator/llm.py:426, backend/src/curator/llm.py:667, backend/src/curator/llm.py:870, backend/src/curator/llm.py:1022, backend/src/curator/llm.py:1154, backend/src/curator/llm.py:1168
- Evidence: `run_prompt` passes `json_mode=contract.supports_json_mode` and `temperature=contract.temperature`. Ollama honors JSON mode with `payload["format"] = "json"` and DeepSeek uses `response_format={"type":"json_object"}`. Claude Code, Antigravity, and Codex CLI clients accept `json_mode`/`temperature` parameters but mark them unused and flatten all messages through `_messages_to_prompt`. This means the same `PromptContract` is materially different across providers: API/Ollama paths get native JSON constraints and temperature control, while CLI paths rely only on natural-language "Return ONLY JSON" text and provider defaults.
- Fix sketch: Add an explicit provider capability layer (`native_json_mode`, `temperature_control`, `system_role_native`, `supports_seed` if useful). Have the renderer/runner apply one normalized JSON-output envelope for non-native providers, record capability degradation in `prompt_runs`, and add golden tests that compare rendered request intent for Ollama, DeepSeek, Claude, Antigravity, and Codex. If a contract requires strict JSON, make the absence of native JSON an explicit contract/runtime decision rather than an ignored kwarg.
- Blast radius: All registered JSON prompt families, cross-provider prompt evals, failover behavior, CLI-backed cloud use, and any future prompt-v2 consistency benchmark.
- Suggested PR: `refactor/llm-provider-capabilities`

### [G09-3] (a/h) S2 - Prompt traces can record the wrong provider and can stay pending after call failure
- Loc: backend/src/curator/prompting/trace.py:36, backend/src/curator/prompting/trace.py:55, backend/src/curator/prompting/runner.py:139, backend/src/curator/prompting/runner.py:151, backend/src/curator/prompting/runner.py:174, backend/src/curator/llm.py:1359, backend/src/curator/llm.py:1364, backend/src/curator/llm.py:1369
- Evidence: `start_prompt_run` records provider/model before the model call. For a `FailoverClient`, `provider_name()` reads the current `active_provider` at trace-start time, but `FailoverClient.chat()` can fail the active provider, call a fallback, and only then update `_active_idx`. The prompt row can therefore claim the primary provider/model even when the output came from the fallback. Separately, `run_prompt` starts the trace before `client.chat()` but only calls `finish_prompt_run()` after parsing/validation. If `client.chat()` raises, the prompt run is left open/pending with no failure status, latency, or error hash.
- Fix sketch: Make model calls return provider provenance or expose a `last_provider_metadata` object from `FailoverClient`, then update the prompt row with actual provider/model after the successful call. Wrap `run_prompt` in a failure path that closes the trace with a failed/error status and validator error text when the model call or parse pipeline raises.
- Blast radius: Prompt trace UI, query/synthesis audit, cross-model eval attribution, failover debugging, and any metrics that compare provider quality or latency.
- Suggested PR: `fix/prompt-trace-provider-provenance`

### [G09-4] (e/f) S2 - Backend and plugin prompt registries are separate policy islands with a misleading shared name
- Loc: backend/src/curator/prompting/registry.py:17, backend/src/curator/prompting/contracts.py:27, plugin/src/context/promptRegistry.ts:1, plugin/src/context/promptRegistry.ts:15, plugin/src/context/promptRegistry.ts:47, plugin/src/context/promptRegistry.ts:78, plugin/src/context/systemPrompt.ts:17, plugin/src/context/systemPrompt.ts:75
- Evidence: Backend `PromptRegistry` is the versioned `PromptContract` registry promised by the spec. Plugin `promptRegistry.ts` is not a prompt contract registry; it is a UI surface policy registry for tool boundaries and recency anchors. It owns critical language like "NO tools and NO filesystem access", allowed roots, read-only edit bans, and selection focus. `systemPrompt.ts` separately owns the sidechat base prompt and language bridge. There is no shared manifest that says which constraints are backend-global, plugin-only, or provider-adapter-only, and the duplicated "registry" name hides that these systems cannot validate or diff each other.
- Fix sketch: Rename/split the plugin module to a more precise name such as `surfacePromptPolicy.ts`, keep it as the canonical frontend surface policy, and add a small generated/shared prompt-policy manifest for cross-cutting invariants that must match backend behavior (read-only source truth, language bridge, math delimiters, evidence/citation rules). Add tests that compare the shared manifest values across backend docs/registry and plugin prompt assembly where overlap is intentional.
- Blast radius: Plugin sidechat, quick query popover, backend prompt docs, prompt-v2 governance, and future attempts to reconcile backend and frontend prompt behavior.
- Suggested PR: `refactor/prompt-policy-boundaries`

### [G09-5] (a/h) S2 - Validators are narrower than the spec-level prompt safety contract
- Loc: docs/specs/system_behavior/SYSTEM_BEHAVIOR.md:1078, docs/specs/system_behavior/SYSTEM_BEHAVIOR.md:1083, backend/src/curator/prompting/validators.py:24, backend/src/curator/prompting/validators.py:86, backend/src/curator/prompting/validators.py:115, backend/src/curator/prompting/validators.py:128, backend/src/curator/prompting/validators.py:198, backend/src/curator/prompting/families/source_map.py:87, backend/src/curator/prompting/families/query.py:162
- Evidence: The spec requires valid JSON, only real Curator/source ids, no invented wikilinks, confidence ranges, source-truth separation, no mutation of `03_Notes`/`04_Resources`, and math delimiter preservation. The implemented validator registry covers JSON model parsing, `source_span_ids`, optional `requires_source_spans`, optional `no_unknown_wikilinks`, a regex for read-only source mutation, confidence range, generated English, and relation endpoints. No prompt family currently declares `no_unknown_wikilinks`; `curator.source_map` asks to preserve math but only declares `no_source_truth_pollution`; `curator.query_router` has only `confidence_range`; there is no generic validator for invented `ENT-`/`CON-`/`ATM-` ids or math delimiter preservation. The source-truth mutation regex also only catches verbs within 40 characters of a named read-only directory, so broader "rewrite the source/original note" phrasing can slip past.
- Fix sketch: Expand validators to match the spec contract, then make each family declare the relevant set. Add deterministic validation contexts for allowed node ids/wikilinks, math-delimiter preservation checks for source-map/vision-derived prompts, and stricter source-truth mutation patterns. Backfill tests that prove the validator fails on invented `CON-`/`ATM-`/`ENT-` ids, invented wikilinks, and broken math delimiters.
- Blast radius: Prompt families, retrieval/query answer validation, graph extraction, source-map quality, repair retries, and all callers that currently assume `result.ok` means the full spec contract passed.
- Suggested PR: `fix/prompt-validator-contract`

### [G09-7] (a) S3 - Latest prompt version lookup is lexicographic
- Loc: backend/src/curator/prompting/registry.py:31, backend/src/curator/prompting/registry.py:35, backend/src/curator/prompting/registry.py:36, backend/src/curator/prompting/registry.py:37, backend/tests/test_prompt_registry.py:35
- Evidence: `PromptRegistry.get(prompt_id)` chooses the latest version with `sorted(versions)[-1]` and comments "Latest by string-sorted version (v1, v2, ...)." This will choose `v9` over `v10` and has no test for multi-digit versions. Prompt v2 work is likely to add more versions; leaving this as string order creates a latent wrong-contract bug.
- Fix sketch: Parse `vN` numerically for simple prompt versions or define a semver-compatible prompt-version type. Add a unit test registering `v2`, `v9`, and `v10` and asserting unversioned `get()` returns `v10`.
- Blast radius: Any caller using unversioned `REGISTRY.get(...)`, prompt eval fixtures, prompt CLI display, and future v2/v3 migrations.
- Suggested PR: `fix/prompt-version-ordering`

### [G09-8] (e/h) S3 - Vision prompts are unregistered and untraced despite affecting ingestion output

Record prompt id/version/model/hash in the vision cache and add offline fixtures for common CLI/API noncompliance.
- Blast radius: PDF VLM ingest, interactive PDF transcription, image-source ingestion, vision cache invalidation, and reproducibility of L1 content.
- Suggested PR: `refactor/vision-prompt-contracts`

## Positives (keep / do-not-break)
- The backend has a real contract-driven prompt foundation: `PromptContract` captures id/version/family/role/input/output/templates/validators/retry/temperature, and `PromptRegistry.register()` rejects duplicate `prompt_id@version`.
- The renderer uses `{{ field }}` placeholders and JSON-encodes non-string values, avoiding the common `.format()` collision with literal JSON braces in prompt templates.
- `run_prompt()` already centralizes render -> trace -> call -> parse -> validate -> one repair retry for the registered prompt path, and tests cover registry completeness, rendering determinism, validator names, trace persistence, and repair behavior.
- The core registered families cover the spec-required ids, and the knowledge-unit prompt has already advanced to `v3` with explicit support roles, formula centrality, generated-English expectations, and source-span validation.
- The plugin's `promptRegistry.ts` is a good local consolidation for sidechat/popover boundary rules; keep that consolidation even if the module is renamed or linked to a shared manifest.
- `vision.py` has careful temp-PNG lifecycle management, transient path sanitization, and provider-noise normalization. Preserve those guardrails while adding prompt governance.

## Open questions for the human

- For prompt architecture v2, is the target a single global `v2` line across every prompt family, or family-specific versions where only changed contracts advance?
- Should CLI providers without native JSON/temperature controls be allowed for strict extraction contracts, or should strict prompts prefer providers with enforceable JSON mode and use CLI providers only with explicit degradation metadata?
- Are persona interview, lint relink, contradiction repair, and vision transcription considered first-class prompt families for `wiki prompt list`, or intentionally outside that command?
