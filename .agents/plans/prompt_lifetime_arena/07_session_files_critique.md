# Independent critique: immutable session revisions

Date: 2026-09-14. Design review only; no application or production writes.
Read `05_session_consensus.md`, `05_handoff_consensus.md`, current
`sessionStore.ts`, and the existing adapter rename boundary.

## Verdict

The immutable-file alternative can remove the shared mutable-file race without
adding a native locking dependency. It is a different storage contract from the
05 consensus and needs an explicit superseding decision and migration rehearsal.
It is not complete merely because every individual rename is atomic: acceptance,
retention markers, compaction witnesses and diagnostic receipts must remain
deterministic under incomplete directory observations and independent sync.

Use one complete **session** per revision, not the complete multi-session store
per save. The current coalescing rationale still applies: one send currently
requests several saves. Keep coalescing and measure bytes/files generated by a
streaming conversation. A full-revision format is acceptable only with actual
compaction, not an indefinitely growing transcript log. Preserve all message
fields, replay and thumbnails in the accepted complete revision.

## Concrete counterexamples and required rules

### Concurrent writer and age GC

GC reads old revision R, a user publishes newer revision S, then GC publishes
its marker for R. A terminal deletion marker would discard the fresh activity.
A conditional marker must suppress only revisions at or below its recorded
revision bound, within that session, and only according to its recorded age
policy. S survives if it ranks above that bound. The reverse publication order
has the same result. No shared canonical file is overwritten.

An update does not become newer solely because it renames later. Preserve an
explicit total revision order, including the existing timestamp/message-count
ordering and deterministic unique-ID tie breaker. For a locally observed edit,
generate a revision greater than the observed predecessor even if the wall clock
moves backward. Do not claim unseen cross-device activity is causally newer:
offline clock skew can still make its revision lose under whole-session LWW.

The CLI count must describe revisions/sessions newly suppressed in its observed
state; it cannot promise a concurrent newer session remains absent when the
command returns. Document this exact change from terminal age deletion. Explicit
user deletion remains terminal and dominates all revisions regardless of clock.

### Marker aggregation

Two collectors can publish different revision bounds and age cutoffs. Preserve
the union of their predicates. Taking the maximum bound from one marker and the
maximum cutoff from another invents a predicate neither collector approved.
Either prove one predicate subsumes another or preserve both in compaction.
If revision rank alone defines suppression after initial age eligibility, say
so explicitly and do not ambiguously describe age as a second read-time test.

### Compaction is itself concurrent writing

C1 observes R1/R2, C2 observes R2/R3. If each writes a mutable checkpoint and
deletes all other files, C1 can overwrite C2 and erase R3. Checkpoints therefore
must also be uniquely named immutable publications. A compactor may delete only
the exact immutable inputs it read and whose state its durable output subsumes.
It must never delete unobserved filenames discovered after publishing output.
Publish and validate the replacement before removing any consumed input.

The output must contain the complete winning session, required diagnostics,
terminal marker state and retained conditional marker predicates. A revision
number alone is not a replacement for the last transcript or capsule bytes.
Winner witnesses prevent a stale offline revision from reviving after prior
winner files were pruned. They do not authorize dropping the winning payload.
Concurrent compactor outputs converge by the same deterministic acceptance
rules; their filenames and creation times cannot determine the winner.

Cross-device delivery may send deletion of consumed input before the replacement
checkpoint. Directory absence therefore never proves session deletion or owner
release. Keep the last locally accepted complete state until explicit accepted
replacement/marker evidence arrives. A newly bootstrapped device with an
incomplete transfer cannot honestly call that absence a complete empty store.
Report/retry incomplete recovery; do not silently initialize authoritative empty
state. No finite peer-acknowledgement floor is assumed.

### Receipt ownership and last-copy loss

A receipt for turn T is copied into winning revision R2, then deleted by local
compaction. An offline R3 wins LWW but lacks T or the capsule added on R2. The
receipt's diagnostic bytes disappear even though a later accepted snapshot may
still contain a rendered PTR link. Therefore receipt deletion is not justified
by incorporation into one currently accepted revision alone.

The narrowest safe initial rule is to retain independently named diagnostic
receipts for the lifetime of the non-terminal session and deduplicate only
identical durable receipts with an explicit replacement witness. This grows
with actual recorded diagnostics, not transcript-save count. Acceptance still
decides which saved turns are current owners; a losing/absent turn's receipt is
not automatically an active DB owner. Retained receipt bytes allow later
accepted references to recover without fabrication. A terminal session delete
can release both owner and receipt data under the existing deletion policy.

If the implementation instead wants to discard receipts for a removed turn or
conditionally pruned session, it needs a proof that any future surviving
revision carries complete evidence independently. A conditional GC marker
permits newer activity, so it lacks the finality of explicit deletion. Deleting
the last receipt under that marker can break a late offline revision containing
only the pre-saved turn placeholder. Retain it until evidence closure is proved;
do not quietly equate conditional retention with terminal deletion.

This is a real storage-cost consequence. Do not claim that automatic session
GC immediately reclaims every diagnostic byte if recoverable receipt storage
remains. Logical session removal and physical reclamation need separate counts.

### Publication and corrupt inputs

The existing `VaultTextAdapter` already declares `rename`, and
`atomicWriteVaultText` uses a temporary write plus rename. The design can reuse
that concrete surface with unique destination IDs. Do not claim its mock tests
prove filesystem durability or cross-platform atomicity. Test the actual
desktop adapter and Python publication paths on supported platforms.

Readers ignore unpublished temporary names. Validate version, session/operation
identity, full payload and digest before admitting a final file. Conflicting
bytes under one supposedly immutable operation ID are corruption, not LWW.
Unreadable/corrupt candidate files must not be interpreted as no owners or
permission to delete their presumed predecessors. Preserve and report them.
Old `sessions.json` writers must be quiesced for migration; dual authoritative
writers would recreate the ambiguity this design removes.

## Minimum adversarial implementation gates

1. Both save/conditional-prune publication orders, explicit delete racing save,
   backward local clock, equal timestamp ties and a late offline snapshot.
2. Two concurrent compactors with intersecting input sets; crash before output
   rename, after rename and during exact-input removal. Compare full transcripts
   and every capsule field, not only session counts.
3. Deliver replacement/input deletions in both sync orders, remove the current
   directory entry transiently, and bootstrap from an incomplete transfer.
4. Receipt publication after conditional prune, terminal delete, and a winner
   that lacks the original turn; then deliver a newer snapshot containing the
   turn/PTR. Prove complete diagnostic recovery or explicit missing evidence.
5. Preserve the existing loaded-session-ID and mutation-epoch corrections from
   05: immutable storage alone does not stop the view saving old messages under
   the newly selected session or overwriting newer in-memory edits.
6. Measure a realistic multi-turn streaming save/compact cycle for serialized
   bytes, final file count and retained receipt bytes. Validate native adapter
   publication rather than assuming a new runtime API exists.

The alternative is viable if these rules become the actual contract. The main
unclosed issue is last-copy reclamation for conditional-pruned sessions with
late receipts/offline turns, not the absence of a native lock.
