# Critique on Synchronization and Cache Safety Proposal
Date: 2026-09-11 | Agent Persona: Backend / Schema Adversarial Reviewer

## 1. Vulnerabilities & Flaws

The read-only inspection and zero-sources findings are credible, directly bounded, and sufficient to justify a patch. The plan correctly refuses to mistake table locality for lack of value. I support these two changes as the next release ahead of a new UI or history-expiry policy. The following details need tightening before implementation.

1. **Revalidation repairs the confirmation gap, not cache lifecycle synchronization.** A writer can start after the final occupancy probe, just as a prompt artifact writer can publish after GC releases its database lock. This need not be malicious or “uncooperative”: a normal already-running temporary-vault job can outlive removal of its vault directory. The proposed caveat is necessary, but wording should explicitly acknowledge ordinary background writers. Do not claim all cache deletion races are fixed. The minimal patch can still fix stale-plan deletion as one concrete defect; a shared cache ownership protocol is a distinct requirement if concurrent producer safety is promised.
2. **FTS shadow exclusions must be identity-based and verifiable.** Merely exempting names ending in `_data`/`_config` or starting with `search_documents_fts` would let an unrelated ordinary table carry durable rows unnoticed. Discover actual virtual tables and their shadow types (`PRAGMA table_list` on supported SQLite); additionally verify the owning virtual-table declaration is the known FTS schema. A populated logical FTS table must retain the cache. If trustworthy classification is unavailable, preserve the namespace rather than guess. Avoid initializing/migrating just to learn the schema.
3. **A known table set is not proof of a known schema.** Empty but malformed user tables can match all expected names while differing in columns/types or carrying custom triggers/views. Since the proposal already promises unknown/partial layouts remain untouched, specify a bounded fingerprint or equivalent expected layout comparison to a trusted fresh schema, without executing that schema against candidates. Alternatively conservatively reject unexpected objects and missing required columns. Do not let “all current table names exist” stand in for recognition.
4. **The recursive-delete proof must cover the whole namespace.** The proposal mentions this but leaves file taxonomy open. Before implementation inventory actual fresh cache fixtures and config path writers. Deleting a known-empty DB while also removing an unknown prompt transcript or sync journal is a policy change. Unknown files should simply keep the namespace; adding special deletion rules for them is beyond this patch. SQLite WAL/SHM are associated state, and probes must see committed WAL history before they are allowed.
5. **Canonical root and namespace identity checks require distinct tests.** `/tmp/../Users/...` must not satisfy the temporary-prefix rule; a symlink in the recorded root path can likewise turn a lexical temp prefix into a live non-temp directory. Reject namespace, marker and DB symlinks as planned; marker contents changing without inode replacement must also invalidate the candidate. Compare device/inode/type, not only path text or mtime. Device/inode does not establish content stability, so occupancy and marker rereads remain necessary.
6. **Read-only means no logical/schema mutation; exact bytes need a WAL-aware contract.** The key observed defect is schema creation/stamping. `mode=ro` SQLite can still interact with shared-memory coordination in an existing WAL namespace. Do not use `immutable=1`, and do not overclaim “no bytes anywhere can ever change” without measuring WAL-sidecar behavior. Tests should prove database logical rows/schema/version remain identical and original durable files are preserved, while explicitly verifying the intended filesystem-level promise where feasible.

## 2. Suggested Alternatives

Keep v0.82.6 scoped to the demonstrated collector contract violations: use a non-healing SQLite connection, require recognized schema plus no durable rows, retain unexpected files, and revalidate current identity/root/content after confirmation. Add deterministic tests for those exact violations and document that fresh emptiness does not establish exclusive ownership of a concurrently written cache.

Use the fresh schema definition only as a trusted expected model; never apply it to the candidate to make inspection easier. A disposable in-memory/temp initialized reference is acceptable if tests demonstrate the comparison cannot classify unknown persistent structures as infrastructure. Prefer a small explicit object policy over a generic schema-management subsystem.

Prompt-run cap work should not be smuggled into this patch as `BEGIN IMMEDIATE` alone. Parent critique and production-path tracing confirmed the run exists across provider and publication transactions (`runner.py:205–285`; `community_reports.py:284–311`; `graph_index.py:253–312`). That transaction fix would narrow one race while leaving ordinary delayed publication dangling. Keep its observed reproduction and design a real run lifetime/reservation mechanism separately; if the only immediate option is reducing the cap's capability, present that product choice to the user.

No new deletion window, no dashboard trigger, no production GC, no tombstone expiration, and no reindex are required to repair the two independently proven cache defects. The remaining B1/B2 work must remain visible after this patch.
