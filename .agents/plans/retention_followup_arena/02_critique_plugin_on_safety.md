# Critique on Synchronization and Cache Safety Proposal
Date: 2026-09-11 | Agent Persona: Plugin / Cross-Writer Retention Adversary

## 1. Vulnerabilities & Flaws

The verified cache defects justify a patch before adding Dashboard execution. I accept the read-only probe, all-application-row emptiness floor, retained unknown data, and explicit limited claim for final revalidation. The proposal does not justify any new deletion window. Four points must be locked before implementation rather than left as appealing prose.

1. **“Read-only URI” is necessary but not a whole filesystem non-mutation proof.** Normal SQLite WAL readers can need/create shared-memory coordination sidecars depending on layout and SQLite version; closing the last connection can affect sidecars. `immutable=1` would avoid coordination by ignoring active changes, which is unsafe and correctly rejected here. State the exact claim as no application/schema/database-content writes or migration, and exercise a live writer with committed WAL rows. Do not assert byte-for-byte equality for every WAL/SHM file while a writer is running. For a closed partial-schema fixture, byte-for-byte database equality is both meaningful and required.

2. **“Unrecognized layout” and “probe unknown populated tables” need an exact relationship.** If any unknown table immediately rejects a database, its contents need not be queried, but a known empty DB with harmless empty extension tables would be retained. If unknown empty tables are allowed, this is a different layout policy and needs an explicit test. Prefer a current recognized schema floor plus no rows in every discovered non-infrastructure ordinary/logical virtual table; unknown populated tables always reject. Missing required base tables or an unsupported schema-version stamp rejects before occupancy is interpreted. Avoid hardcoding every current application column or exact trigger SQL: empty old layouts can safely be retained, but unrelated schema changes must not make the collector silently destructive.

3. **Metadata exemptions can accidentally become deletion exemptions.** Do not skip every table with `_fts`, `sqlite_`, or “schema” in its name. Exempt only SQLite-owned sequence bookkeeping and the exact recognized schema-version metadata; prove that every exempt FTS shadow table belongs to a recognized logical FTS table. Query logical FTS occupancy. A maliciously or accidentally named ordinary table such as `search_documents_fts_history` with a durable row must retain the cache. The supported Python SQLite runtime's `PRAGMA table_list` availability is an implementation fact to check, not a new dependency assumption.

4. **Namespace-file preservation must be specified, not silently replaced by “any non-DB file means no GC”.** Existing fixtures include `vault_root` and a current initialized DB (`test_gc_cache_sweep.py:26–41`), so those are mandatory accepted infrastructure. Recognized SQLite WAL/SHM sidecars can contain committed history and must be read through SQLite, not counted as random debris. Any allowlist for runtime subdirectories/logs needs an inventory and a reason each file is safe; no such inventory is established here. Retaining unexplained files is correct for this patch, with a visible explanation/follow-up if it means real previously collected temp namespaces remain. The regression for a genuinely empty current fixture is indispensable: a universal no-op does not fulfill the existing collector contract.

The proposed identity/revalidation checks close observed changes between preview and execution only. A writer can still insert a row after the final query while `rmtree` starts. Do not describe this as full TOCTOU safety in docs, tests, or release notes. This bounded correction is legitimate because it narrows existing destructive behavior; it must not be used as the safety proof for introducing new active-session deletion paths in Dashboard.

## 2. Suggested Alternatives

Lock the patch's proof as a small centralized predicate: recognized real namespace; unchanged planned directory identity; unchanged valid regular marker; absent canonical temp root; recognized, readable, non-symlink SQLite state; no durable application rows observed using ordinary WAL-aware reads; no unexplained namespace content. The identical predicate is used during plan and immediately before removal. Retain an unverifiable candidate instead of trying to repair it. Document final-check limitations once, accurately.

Use representative durable-row tests that cover semantic classes (source, tombstone, prompt/query history, local job history, logical FTS row, unknown ordinary table), plus known empty infrastructure. Include missing DB with unexpected standalone file: recursive deletion must not assume no SQLite means no meaningful bytes. A renamed/replaced directory with the same marker text must fail the identity check, and a newly created source/history row between plan and confirm must produce zero removals.

The separate plugin finding must survive synthesis as an immediate follow-up: backend session read/split/atomic-replace (`gc.py:381–399`) and Obsidian's process callback (`sessionStore.ts:90–102`) have no shared serialization. A stale sidebar message clone can also be copied into the replacement selected session after GC. Cache revalidation and SQLite prompt-run locking fix neither issue. Do not add `gc run` in Dashboard, call its enabled state a “safety check,” and consider retention shipped. Design and test writer coordination plus selected-session reconciliation before that action, while preserving complete active-session replay and thumbnails. Preview/policy UI can be a partial milestone if labeled as such; it cannot close B1/B2.

Consensus: proceed with the narrow existing-GC safety patch, provided it preserves the genuinely empty-cache case, makes no atomic filesystem exclusion claim, and keeps the backend/plugin session-writer problem explicitly queued. No user product choice is needed to stop a collector from deleting retained state. New finite windows for job/query/compiler history remain separate decisions.
