# 📖 사용자 가이드: InCurator 마스터하기

이 가이드는 **Curator Engine**을 운영하고 지식 DAG를 관리하는 데 필요한 기술적인 세부 사항을 제공합니다. 시스템의 철학에 대한 전반적인 개요는 [README](../../README.md)를 참조하세요.

---

## 📋 사전 준비 사항

시스템을 설치하기 전에 다음 도구들이 설치되어 있어야 합니다:

1.  **Python 3.10+**: 시스템의 핵심 로직이 Python으로 작성되었습니다.
2.  **Obsidian (필수)**: 지식 베이스의 시각화 및 편집을 위한 기본 도구입니다.
3.  **Node.js**: 검색 엔진(QMD) 빌드 및 MCP 서버 구동을 위해 필요합니다. (`./install.sh` 실행 시 자동 설치를 시도합니다.)
4.  **Curator Engine 백엔드 (Ollama 및 구독형 LLM)**: 시스템 구동을 위해 하나 이상의 모델 백엔드가 필요합니다.
    - **구독 서비스 계정/ID**: Gemini, Claude, OpenAI 등을 연동합니다. 복잡한 설정 없이도 구독 중인 **서비스 ID (Project ID)**나 **계정 로그인**만으로 CLI에서 간편하게 사용할 수 있습니다.
    - **Failover (대체 작동)**: 로컬(Ollama)과 클라우드를 함께 등록하면, 특정 서비스 장애 시 자동으로 다른 모델로 전환하여 파이프라인을 중단 없이 지속(Fallback)할 수 있습니다.

> [!NOTE]
> **검증된 개발 환경**
> 본 시스템은 다음 환경에서 모든 기능 및 사용성 테스트가 완료되었습니다:
> - **운영체제**: Linux (Ubuntu 24.04), macOS
> - **하드웨어**:
>   - **Linux**: NVIDIA GeForce RTX 4070 Ti 12GB, RAM 64GB
>   - **macOS**: Apple Silicon (8GB RAM 환경 테스트 완료)
> - **에이전트**: **antigravity** 에이전트 환경에서 검증
> - **최소 사양 및 로컬 성능**: 
>   - 검색 엔진(QMD) 구동을 위한 **최소 2.5GB VRAM**과 선택한 LLM 모델 크기만큼의 추가 VRAM이 필요합니다.
>   - **8B 파라미터 모델**(예: DeepSeek-R1 8B) 사용 시, 시스템 전체적으로 **약 10GB 이상의 VRAM**을 점유하는 것을 확인했습니다 (12GB VRAM 환경 권장).
>   - Ollama를 통해 CPU+GPU 혼합 추론이 가능하지만, 처리 속도가 매우 느려 실용적인 큐레이션이 어려울 수 있습니다. 가급적 모델 전체가 VRAM에 올라가는 환경을 권장합니다.

> [!TIP]
> **다중 기기 동기화**
> 여러 기기에서 동일한 Vault를 사용하려는 경우 **Syncthing** 사용을 강력히 권장합니다. 동기화 과정에서 활발히 수정 중인 데이터베이스(SQLite) 파일이 동시에 전송될 경우 데이터가 파손될 위험이 있습니다. Syncthing의 **제외(Ignore)** 기능을 활용하여 실시간으로 변하는 DB 정보가 동기화 대상에서 제외되도록 설정해야 합니다. 자세한 방법은 [동기화 제외 가이드](./SYNC_IGNORE_GUIDE.md)를 참조하세요.

## 🧭 InCurator 운영 원칙 (Operational Principles)

InCurator의 강력한 성능을 유지하고 지식을 안전하게 관리하기 위해 다음 원칙을 준수하는 것을 권장합니다.

-   **단일 진실 공급원 (Single Source of Truth)**: 프로젝트마다 `wiki init`을 수행하여 여러 개의 작은 지식 베이스를 만드는 것보다, 당신의 모든 지식을 집약할 **단 하나의 메인 보관소(Vault)**를 운영하세요. 지식은 한곳에 모여 응집될 때 비로소 유기적으로 연결되고 새로운 통찰로 **Increment(증분)** 됩니다.
-   **기계의 영역 존중 (Hands-off `.curator`)**: `.curator/` 폴더는 오직 에이전트와 시스템만을 위한 '기계의 공간'입니다. 이곳은 사람이 읽고 편집하기 어렵게 설계되었으며, 수동으로 파일을 수정할 경우 지식 그래프의 정합성이 깨질 수 있습니다. 웬만한 상황에서는 이곳을 직접 건드리지 마세요.
-   **자가 치유와 무결성 (Self-Healing)**: 만약 지식 그래프가 오염되었거나 링크가 깨졌다고 느껴진다면, 직접 수리하려 애쓰지 말고 `wiki sync` 명령을 실행하세요. InCurator는 스스로 오류를 추적하고 논리적 무결성을 회복하는 자가 치유 능력을 갖추고 있습니다.
-   **워크스페이스의 유연성**: 지식의 저장소(Vault)는 하나여야 하지만, 작업을 수행하는 **워크스페이스(Workspace)**는 어디에 있어도 상관없습니다. 당신의 개발 프로젝트 폴더나 임의의 작업 디렉토리에서 중앙의 메인 Vault와 연결하여 사용하세요. '지식의 창고(Vault)'는 하나지만 '지식의 작업실(Workspace)'은 무한히 늘어날 수 있습니다.

## 🚀 빠른 시작

### 1. 설치
설치 스크립트를 실행하여 환경을 설정하고 필요한 구성 요소를 빌드합니다.
```bash
./install.sh
```

### 2. 저장소(Vault) 초기화
지식 저장소로 사용할 디렉토리를 선택하고 초기화합니다.
```bash
wiki init <path/to/your/obsidian-vault>
```

### 3. 지식 소스 등록
사용자가 보유한 원본 파일(PDF, Markdown, HTML, Text)을 Curator에게 전달하여 등록합니다.
```bash
wiki add <file>
```
이 명령은 **지식 등록 및 컴파일 (L1~L3)**를 수행하며, 원본 데이터를 파싱하여 다음과 같은 작업을 진행합니다:
- **L1 Contexts**: 원본 데이터를 1:1로 요약하고 지식 후보를 식별합니다.
- **L2 Atoms**: 더 이상 쪼개지지 않는 독립된 사실을 추출합니다.
- **L3 Concepts**: 원자(Atoms)들을 주제별 구조로 엮습니다.

### 4. 지식 활용 (검색) 및 L4 큐레이션
지식을 검색하면 시스템이 필요한 경우 최종 L4 파이프라인을 자동으로 실행하여 Concepts를 Exhibition으로 합성합니다. 수동으로 실행하려면 다음 명령을 사용합니다.
```bash
wiki curate
```
- **L4 Exhibitions**: 고차원 개념(Concepts)들을 에이전트가 바로 사용 가능한 최적화 패키지로 합성합니다.

## 🛠️ 핵심 명령어

| 명령어 | 설명 | 사용 시점 |
| :--- | :--- | :--- |
| `wiki add <file>` | 새로운 소스를 등록하고 L1~L3를 빌드합니다. | 새로운 원본 정보가 있을 때 |
| `wiki curate` | L3 ➡️ L4 LLM 파이프라인을 실행합니다. | Exhibition을 수동으로 빌드하거나 업데이트할 때 |
| `wiki sync` | 무결성을 검증하고 DAG를 복구합니다. | 링크가 깨졌거나 노드 간 동기화가 필요할 때 |
| `wiki query "..."` | 검색 후 답변을 합성합니다. | RAG 기반의 빠른 답변이 필요할 때 |
| `wiki status` | 저장소 상태와 통계를 표시합니다. | 지식 생태계의 건강 상태를 확인할 때 |
| `wiki reindex` | 검색 인덱스를 다시 빌드합니다. | 수동 편집 후 검색 가능하게 만들고 싶을 때 |

## 📂 계층 구조 이해하기

Curator는 모든 주장에 근거가 있음을 보장하기 위해 **방향성 비순환 그래프(DAG)**를 구축합니다.

1.  **01_Contexts (L1)**: 소스의 원래 의도와 메타데이터를 보존하는 요약본입니다.
2.  **02_Atoms (L2)**: 독립적인 원자 단위의 주장입니다. 제텔카스텐의 "영구 메모"와 같습니다.
3.  **03_Concepts (L3)**: 여러 소스에 걸친 원자들을 연결하는 상위 테마 그룹입니다.
4.  **04_Exhibitions (L4)**: 에이전트를 위해 준비된 최종 "전시물"입니다. 특정 작업에 맞춰 구성되며 증거에 기반합니다.

## 🎨 워크스페이스 관리

워크스페이스(`01_Workspaces/`)는 **아티스트** (인간 + 에이전트)가 작업하는 공간입니다. 각 워크스페이스에는 `curate.yml` 파일이 있습니다.

### `curate.yml` (지식 요구 명세서)
이 파일은 Curator에게 에이전트를 위해 어떤 지식을 "전시"할지 알려줍니다.
```yaml
project: "Gaussian Splatting Research"
scope: "concepts" # all | concepts | exhibitions
min_confidence: 0.8
boost_terms: ["depth distortion", "normal consistency"]
```
에이전트가 MCP를 통해 검색할 때, Curator는 이 명세서를 사용하여 가장 관련성 높은 "전시물"을 필터링하고 우선순위를 정합니다.

## 🔄 피드백 루프 (HITL)

1.  **순방향 (Forward Pass)**: `wiki curate`를 사용하여 지식을 구축합니다.
2.  **합성 (Synthesis)**: 워크스페이스에서 에이전트와 자연스럽게 대화하며 새로운 통찰을 이끌어냅니다. 이러한 대화 과정에서 자연스럽게 사전 지식의 오류를 발견하면 MCP 도구로 즉시 노드를 수정할 수 있습니다.
3.  **수리 (Backprop)**: 노드 수정 시 `wiki sync`가 자동으로 실행되어 그래프를 역추적하고 관련 상위 노드들을 재작성하여 무결성을 유지합니다.
4.  **승격 (Promotion)**: 확정된 통찰을 `02_Wiki/`로 이동시킵니다.
5.  **순환 (Loop)**: Curator는 다음 주기에서 `02_Wiki/` 내용을 새로운 소스로 자동 인식하여 흡수하며, 지식을 **점진적으로(Incremental)** 확장하고 경화(Concreting)합니다.
