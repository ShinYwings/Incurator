# 💡 Incurator는 왜 만들어졌는가

## 핵심 문제

PDF, 논문, 연구 메모가 쌓여갈 때 우리가 진정으로 원하는 것은 단순한 키워드 검색이나 일회성 요약이 아닙니다. **내가 이미 축적한 지식을 발판 삼아 새로운 통찰을 유기적으로 쌓아 올리는 것(Increment)**입니다.

대부분의 LLM 기반 위키 및 지식 관리 시스템은 원본 데이터 수집부터 최종 지식 합성까지의 전 과정(Ingest → Structure → Synthesis)을 사람의 개입 없이 AI에게 완전히 일임하려 합니다. 여기서 두 가지 치명적인 문제가 발생합니다.

### 1. 품질의 한계: 피상적인 합성 (Shallow Synthesis)
LLM은 정해진 규칙에 따라 문서를 분해하고 재조립하는 작업에는 매우 뛰어납니다. 하지만 인간의 맥락과 직관적 통찰이 배제된 완전 자동화 파이프라인은 여러 문헌 사이에 숨겨진 진정한 가치와 핵심 인사이트를 짚어내지 못합니다. 가치 있는 합성(Synthesis)을 만들기 위해서는 반드시 **인간의 개입(Human-in-the-Loop)**과 지속적인 상호작용이 필요합니다. 그렇지 않으면 자동화된 위키는 사소한 요약과 왜곡된 연결점들로 가득 차게 됩니다.

### 2. 비용과 자원의 낭비: 단순 작업에 낭비되는 토큰
상용 고성능 추론 모델(Claude 3.5 Sonnet, GPT-4 등)은 복잡한 문제 해결과 심층 추론에 최적화되어 있습니다. 방대한 문서를 파싱하고 요약하며 원자 단위 사실을 추출하는 단순 반복 작업에 비싼 모델을 전면 투입하면 막대한 토큰 비용이 낭비됩니다. 단순한 데이터 전처리와 구조화에는 고비용 추론 모델이 필요하지 않습니다.

---

## 해결책: 컴파일(Compilation)과 추론(Reasoning)의 분리

Incurator는 지식 관리 파이프라인의 역할을 두 단계로 명확히 분리하여 이 문제를 해결합니다.

1. **지식 컴파일 (단순 구조화 작업)**:
   - 문서 구조 파악, 원자적 사실 추출, 주제별 개념 클러스터링 (`Summary → Atoms → Concepts`).
   - 가벼운 로컬 모델(Ollama/SLM) 또는 비추론 모델이 백그라운드에서 자동 처리.
   - 저비용, 자동화, 완벽히 재현 가능한 결정론적 구조.

2. **지식 추론 (창의적 인사이트 도출)**:
   - 질문 응답, 다각도 분석, 새로운 가설 검증 및 합성 (`Query → Insight → New Knowledge`).
   - 고성능 추론 모델과 인간이 실시간으로 대화하며 협업.
   - 고부가가치, 인간 중심, 컴파일된 지식에 기반한 확실한 출처 근거(Grounding).

## 두 개의 공간, 하나의 선순환

이 역할 분리를 명확히 실체화하기 위해 Incurator는 저장소를 두 개의 영역으로 엄격히 분리합니다.

- **AI 전용 공간 (`.curator/`)**: 기계가 읽고 검색하기 위한 지식 그래프(`state.sqlite`)와 점검용 프로젝션(`01_Contexts/`, `02_Atoms/`, `03_Concepts/`, `04_Synthesis/`)이 위치합니다. 원본 문서만 있으면 언제든 통째로 다시 컴파일할 수 있는 재생성 가능 영역입니다.
- **인간 전용 공간 (`02_Wiki/`)**: 인간이 직접 검토하고 승격(Promote)한 영구 지식만이 보존되는 상설 공간입니다.

### 지식 증분의 선순환 (The Lifecycle Loop)
1. **원본 자료**(PDF, 논문, 메모)가 볼트에 등록됩니다.
2. **Curator(백엔드 엔진)**가 이를 분석하여 `.curator/` 내에 계층화된 근거 데이터로 컴파일합니다.
3. **사용자와 에이전트**는 옵시디언 사이드바나 MCP를 통해 컴파일된 지식을 탐색하고 깊이 있게 대화합니다.
4. **승격된 새로운 통찰**은 `02_Wiki/`의 영구 노트로 저장되며, 이는 다시 다음 지식 탐색의 새로운 원본 자료가 됩니다.

지식은 단순히 검색되고 사라지는 것이 아니라, 유기적으로 축적되고 성장(Increment)합니다.
